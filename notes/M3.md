# M3 — Context Engineering

_Cohort notes for the M3 module. Edited as I work through it._

## Step 2 — CLAUDE.md behaviors

Three concrete behaviors the shipped `CLAUDE.md` prevents or enforces:

1. **"Run `pytest` after each substantive change"** — prevents Claude from shipping code that silently breaks existing tests. Without this line, Claude finishes a change and calls it done; tests may be red and nobody checks.
2. **"Don't edit `tests/` to make them pass"** — without this line, Claude will routinely change the test assertion to match whatever the code produces, defeating the purpose of having tests as a spec.
3. **"Always read the task file before writing code"** — keeps Claude from guessing the acceptance criteria. Without it, Claude starts implementing the most plausible interpretation of the task name and can go in the wrong direction for minutes before the user notices.

## Step 3 — bad-context run

Prompt given verbatim: `Add user login to this app.`

Observations from running this against the codebase with zero additional context:

- **Assumed** the app already had a database or ORM — it doesn't. The sandbox is entirely in-memory. Claude would reach for SQLAlchemy + SQLite immediately, inventing schema and a `db.create_all()` call that doesn't match anything in the codebase.
- **Assumed** notes are global and stay global — it did not think to ask whether logged-in users should see only _their_ notes. It would have wired login without isolating note ownership, leaving both users seeing the same list.
- **Did not ask** about scope at all — it would have generated routes for `/login`, `/logout`, `/register`, _and_ a password-reset flow and email verification stub, none of which were requested, tripling the surface area of the change.

## Step 4 — good-context plan

Prompt given with the full context brief (Flask-Login + werkzeug, SQLite users table, no remember-me/reset/email, explicit file list, explicit acceptance criteria, plan-mode instruction).

Claude's plan:

---

### Overview

Keep `app.notes` exactly as-is so existing Task 01 / Task 02 tests keep passing. Introduce a separate per-user SQLite-backed notes store (`app.user_notes: dict[int, list[dict]]`). Guard existing routes with `@login_required`, which forces anonymous visitors to `/login`. Test fixtures use `LOGIN_DISABLED = True` so they run without breaking.

### Step 1 — requirements.txt

Add:
```
flask-login>=0.6
flask-sqlalchemy>=3.1
werkzeug>=3.0
```

### Step 2 — models.py (new file)

- `db = SQLAlchemy()` (unbound, init'd via `db.init_app(app)`).
- `User(db.Model, UserMixin)` with columns: `id` (PK), `username` (unique, not null), `password_hash`.
- Methods: `set_password(plain)` → `generate_password_hash`, `check_password(plain)` → `check_password_hash`.

### Step 3 — Database setup

- `app.config["SQLALCHEMY_DATABASE_URI"] = "sqlite:///sandbox.db"`
- `db.create_all()` called inside `with app.app_context()` at the end of `create_app()`.
- Add `sandbox.db` to `.gitignore`.

### Step 4 — app.py changes

- Import `LoginManager`, `login_user`, `logout_user`, `login_required`, `current_user` from flask_login; import `db`, `User` from models.
- Wire `LoginManager` with `login_view = "login"` and a `@user_loader` callback.
- `app.user_notes: dict[int, list[dict]] = {}` alongside `app.notes`.
- `home()` and `new_note()` get `@login_required`; they read/write `app.user_notes[current_user.id]` with a fallback to `app.notes` when `LOGIN_DISABLED` is active (for test compatibility).
- New `/register` route: validates username uniqueness, hashes password, calls `login_user()`, redirects to `/`.
- New `/login` route: checks credentials, calls `login_user()`, redirects to `/`. Single error message "Invalid username or password" regardless of which field is wrong.
- New `/logout` route (`@login_required`): calls `logout_user()`, redirects to `/login`.

### Step 5 — Templates

- `templates/login.html`: form with `username` + `password`, error block, link to `/register`.
- `templates/register.html`: same shape, link back to `/login`.
- `templates/home.html`: add nav bar with `current_user.username` and a POST form for logout.
- `templates/new_note.html`: same nav bar addition.

### Step 6 — Keeping existing tests passing

- Add `app.config["LOGIN_DISABLED"] = True` to the `app` fixture in `tests/conftest.py`.
- `LOGIN_DISABLED` makes `@login_required` a no-op; `current_user.is_authenticated` is `False`, so routes fall back to `app.notes` — exactly what the current tests expect.
- No test assertions change.

### Sequencing

1. requirements.txt → pip install
2. models.py
3. conftest.py LOGIN_DISABLED patch
4. app.py wiring (LoginManager + user_loader)
5. Modify home + new_note routes
6. Add register / login / logout routes
7. Create login.html, register.html
8. Update home.html, new_note.html
9. `pytest` → all green
10. Manual smoke: anonymous → redirected; register two users; each sees only their notes

## Step 5 — comparison

Side-by-side look at the bad-context output vs. the good-context plan:

1. **Most-impactful line**: `"No 'remember me' cookie, no password reset, no email — out of scope."` This single sentence eliminated an entire category of routes and templates that the bad-context run would have generated. In the bad run, Claude would have scaffolded email verification and password reset automatically because they felt like natural parts of "add user login." The explicit cut killed that scope immediately.

2. **Line Claude may ignore**: `"Store users in a new SQLite table; don't touch the notes schema."` The good-context plan respected this, but there's real tension here — the existing notes are in-memory with no `user_id` field. Claude's plan introduced a separate `user_notes` dict rather than adding a `user_id` column to notes, which technically satisfies the constraint but isn't necessarily what the brief author pictured. A future revision of the brief should say _how_ user isolation works, not just that the notes schema shouldn't change.

3. **Context I wish I'd included**: that the app has **no database at all** right now. The brief assumed Flask-SQLAlchemy would "just work," but the setup — `db.init_app(app)`, `with app.app_context(): db.create_all()`, the instance-path resolution of `sqlite:///` — is non-trivial for a first-timer and not implied by "store users in a new SQLite table." Adding one line like _"The app currently has no ORM or database; you'll need to bootstrap SQLite from scratch"_ would have saved a lot of confusion.
